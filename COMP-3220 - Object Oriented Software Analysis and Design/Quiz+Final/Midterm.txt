## Short / Long Answer Questions

Question 18: Consider the following code:
```java
public interface Coffee {
    double cost();
}
public class BasicCoffee implements Coffee {
    public double cost() {
        return 2.0;
    }
}
```
Suppose we want to support optional add-ons such as Milk, Sugar, Whipped Cream without creating classes like `CoffeeWithMilk`, `CoffeeWithSugar`, `CoffeeWithMilkAndSugar`, `CoffeeWithMilkAndWhippedCream`, etc.

Tasks:
a) Identify the design problem. (2 marks)
b) Which design pattern would improve this design? (2 marks)
c) Describe the classes involved after the proper design pattern applied. (3 marks)

Answer:
a) The design problem is class explosion (combinatorial explosion). Using inheritance for every combination of condiments creates a huge number of subclasses, making the system rigid and violating the Open-Closed Principle.

b) The Decorator Pattern would improve this design.

c) After applying the Decorator Pattern:
- Component: `Coffee` interface with `cost()`.
- Concrete Component: `BasicCoffee` implements `Coffee`.
- Abstract Decorator: `CoffeeDecorator` implements `Coffee` and holds a reference to a `Coffee` object.
- Concrete Decorators: `MilkDecorator`, `SugarDecorator`, `WhippedCreamDecorator` extend `CoffeeDecorator` and add their own cost.
- Client: Wraps `BasicCoffee` with decorators at runtime, e.g., `new WhippedCreamDecorator(new MilkDecorator(new BasicCoffee()))`.

Question 19: Suppose you are building a notification system that supports Email notifications and SMS notifications. Complete the following code skeleton using the Factory Pattern.
```java
public interface Notification {
    void send(String message);
}
public class EmailNotification implements Notification {
    // complete this
}
public class SMSNotification implements Notification {
    // complete this
}
public class NotificationFactory {
    public static Notification createNotification(String type) {
        // complete this
    }
}
```

Answer:
```java
public interface Notification {
    void send(String message);
}

public class EmailNotification implements Notification {
    @Override
    public void send(String message) {
        System.out.println("Sending Email: " + message);
    }
}

public class SMSNotification implements Notification {
    @Override
    public void send(String message) {
        System.out.println("Sending SMS: " + message);
    }
}

public class NotificationFactory {
    public static Notification createNotification(String type) {
        if (type == null) {
            return null;
        }
        if (type.equalsIgnoreCase("EMAIL")) {
            return new EmailNotification();
        } else if (type.equalsIgnoreCase("SMS")) {
            return new SMSNotification();
        } else {
            throw new IllegalArgumentException("Unknown notification type: " + type);
        }
    }
}
```

Question 20: In the Weather Station example from the Observer Pattern:
a) What is the role of the Subject?
b) What is the role of the Observer?
c) Why is this design preferred over directly updating displays?

Answer:
a) The Subject (e.g., `WeatherData`) holds the weather data and a list of observers. When its data changes, it automatically notifies all registered observers by calling their `update()` method.

b) The Observer (e.g., a display screen) registers with the Subject and waits for updates. When notified, it fetches the new data and updates itself (e.g., refreshes the screen).

c) This design is preferred because it's loosely coupled:
- You can add, remove, or replace displays anytime without changing the `WeatherData` class.
- It makes the system flexible, easier to extend, and follows the Open-Closed Principle.

Follow-up: Simplify
Answer:
a) Subject holds data and a list of observers. When data changes, it notifies all observers.
b) Observer registers with Subject, waits for updates, then updates itself.
c) Loosely coupled: you can add/remove displays without changing `WeatherData`.

Follow-up: Does a.) call the `.update()`?
Answer: Yes. The Subject loops through its list and calls `.update()` on every observer. Example:
```java
public void notifySpectators() {
    for(Spectator s : spectators)
        s.update();
}
```

Follow-up: How does the observer refresh the screen?
Answer: Inside its `update()` method, the Observer stores the new data and then calls its own `display()` method to redraw the screen. The Subject only passes the data; the Observer handles its own refresh.

Question 21: State the Open-Closed Principle and explain how the Decorator Pattern supports it. Give an example.

Answer:
Open-Closed Principle: Software entities should be open for extension but closed for modification.

How Decorator supports it:
- Open for extension: You can add new functionality by creating new decorator classes.
- Closed for modification: You never change existing core classes or decorators.

Example (Starbuzz Coffee):
Without Decorator, adding "Soy" requires modifying `Beverage` or creating many subclasses. With Decorator, you just create:
```java
public class SoyDecorator extends CondimentDecorator {
    public double cost() {
        return beverage.cost() + 0.40;
    }
}
```
The original `Beverage` class stays untouched, and Soy is added via extension.

Follow-up: Can you simplify?
Answer:
Open-Closed Principle: Classes should be open for extension (add new features) but closed for modification (don't change existing code).

Decorator supports it: Add new behavior by creating new decorator classes. Never change original classes.

Example: Create `SoyDecorator` to add soy cost. No need to modify `Beverage` or create many subclasses.

Question 22: Compare Factory Pattern and Factory Method Pattern. Discuss: Purpose, Object Creation, Object Behavior.

Answer:

| Aspect | Factory (Simple Factory) | Factory Method |
| :--- | :--- | :--- |
| Purpose | Move `new` out of client code into one central place. | Let subclasses decide *which* object to create, while superclass controls *when* and *how* it's used. |
| Object Creation | One factory class with `if-else` based on a parameter. | Abstract method in superclass; subclasses override to return specific objects. |
| Object Behavior | Factory just returns object; client uses it directly. | Superclass has a template (e.g., `orderPizza()`) that calls factory method and then runs steps like `prepare()`, `bake()`, `cut()`. |

Follow-up: Simplify
Answer:

| Aspect | Factory (Simple Factory) | Factory Method |
| :--- | :--- | :--- |
| Purpose | Move `new` out of client code into one central place. | Let subclasses decide which object to create, while superclass controls when/how it's used. |
| Object Creation | One factory class with `if-else` returns the right object based on a parameter. | Abstract method in superclass; each subclass overrides it to return its own object. |
| Object Behavior | Factory just gives you the object. You do whatever with it. | Superclass has a template (e.g., `orderPizza()`) that calls factory method and automatically does `prepare()`, `bake()`, `cut()`. |

Super Simple Analogy:
- Factory Pattern = A vending machine. Press a button, get a snack.
- Factory Method = A fast-food chain. Head office defines steps: "Take order → Cook → Box → Serve." Each local branch decides *how* to cook it. Steps stay same, product changes.
